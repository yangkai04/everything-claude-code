# Security Bounty Hunter（安全漏洞赏金猎人）

当目标是为负责任披露或赏金提交进行实际漏洞发现时使用，而非宽泛的最佳实践审查。

## 使用场景

- 扫描代码仓库中的可利用漏洞
- 准备 Huntr、HackerOne 或类似平台的赏金提交
- 分类时关注"这个漏洞实际上值钱吗"，而非"这理论上不安全吗"

## 工作原理

优先关注远程可达、用户可控的攻击路径，丢弃平台通常以"信息性"或"超出范围"拒绝的漏洞模式。

## 范围内的漏洞模式

以下是持续有价值的漏洞类型：

| 模式 | CWE | 典型影响 |
| --- | --- | --- |
| 通过用户控制 URL 实现的 SSRF | CWE-918 | 访问内网、窃取云元数据 |
| 中间件或 API 守卫中的认证绕过 | CWE-287 | 未授权访问账户或数据 |
| 远程反序列化或上传至 RCE 路径 | CWE-502 | 代码执行 |
| 可达端点中的 SQL 注入 | CWE-89 | 数据泄露、认证绕过、数据破坏 |
| 请求处理器中的命令注入 | CWE-78 | 代码执行 |
| 文件服务路径中的路径穿越 | CWE-22 | 任意文件读写 |
| 自动触发的 XSS | CWE-79 | 会话劫持、管理员账户接管 |

## 跳过这些

以下漏洞通常信噪比低，或不在赏金范围内（除非项目明确说明）：

- 无远程路径的本地 `pickle.loads`、`torch.load` 或同类操作
- 仅 CLI 工具中的 `eval()` 或 `exec()`
- 完全硬编码命令上的 `shell=True`
- 单独缺少安全响应头
- 没有利用影响的通用限速投诉
- 需要受害者手动粘贴代码的 Self-XSS
- 不在目标程序范围内的 CI/CD 注入
- 演示、示例或仅测试用代码

## 工作流程

1. 先确认范围：程序规则、SECURITY.md、披露渠道及排除项。
2. 找真实入口点：HTTP 处理器、上传、后台任务、Webhook、解析器和集成端点。
3. 在有帮助的地方运行静态工具，但仅作为分类输入。
4. 端到端阅读真实代码路径。
5. 证明用户输入能到达有意义的 sink（汇聚点）。
6. 用最小的安全 PoC 确认可利用性和影响。
7. 起草报告前检查是否已有重复提交。

## 分类示例循环

```bash
semgrep --config=auto --severity=ERROR --severity=WARNING --json
```

然后手动过滤：

- 丢弃测试、演示、fixture、vendor 代码
- 丢弃仅本地或不可达路径
- 只保留有明确网络或用户可控路由的发现

## 报告结构

```markdown
## 描述（Description）
[漏洞是什么，以及为什么重要]

## 漏洞代码（Vulnerable Code）
[文件路径、行号范围及小段代码片段]

## 概念验证（Proof of Concept）
[最小可运行的请求或脚本]

## 影响（Impact）
[攻击者能达成什么目的]

## 受影响版本（Affected Version）
[测试的版本、commit 或部署目标]
```

## 质量关卡

提交前确认：

- 代码路径可从真实用户或网络边界到达
- 输入是真正用户可控的
- Sink（汇聚点）有意义且可被利用
- PoC 可运行
- 该问题未被安全公告、CVE 或开放工单覆盖
- 目标确实在赏金计划范围内
